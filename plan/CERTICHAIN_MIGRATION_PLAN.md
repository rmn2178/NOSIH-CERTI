## 2. Key design decisions (approve or veto)

**D1 — Contract (`contracts/CertificateRegistry.sol`).** Solidity 0.8.20, OZ v5 `AccessControl` + `ReentrancyGuard`. Roles: `DEFAULT_ADMIN_ROLE` (platform), `ISSUER_ROLE` (wallets), `REVOKER_ROLE` (backend revocation key). `mapping(address => bytes32) issuerInstitution` binds each issuer wallet to one institution hash; `issueCertificate` requires supplied `institutionIdHash == issuerInstitution[msg.sender]` (Institution A cannot issue for B — enforced on-chain, brief §5). Struct = brief's `Certificate` + `bytes32 supersedesCertificateIdHash` + `bytes32 reasonHash` stored on revocation. `issuedAt = block.timestamp` (uint64), `expiresAt` uint64 (0 = no expiry; expiry is computed at read time — no on-chain cron). Uniqueness via `exists`/issuedAt guard; issuer recorded as `msg.sender`; `nonReentrant` on writes. Functions: `authorizeIssuer(address,bytes32)` (admin; grants ISSUER_ROLE + binding), `removeIssuer(address)` (admin; revokes role + clears binding), `issueCertificate(Certificate)`, `revokeCertificate(bytes32 certIdHash, bytes32 reasonHash)` (REVOKER_ROLE; once-only), `getCertificate`, `certificateExists`, `getIssuerInstitution`. Events: `IssuerAuthorized`, `IssuerRemoved`, `CertificateIssued` (indexed certIdHash/institutionIdHash/issuer + documentHash, supersedes, timestamps), `CertificateRevoked` (certIdHash, revokedBy, reasonHash). Require-string prefix `CertiChain:`. No PII anywhere on-chain.

**D2 — Revocation permission model (brief §12 allows choice).** App-level: `platform_admin` OR `institution_admin` of the owning institution. Chain-level: backend signs with dedicated `REVOKE_PRIVATE_KEY` holding `REVOKER_ROLE` (never the issuer's browser key, never the deployer key). Reason: required, stored privately in Supabase (`certificate_events.reason`); on-chain only `reasonHash = HMAC-SHA256(HASH_PEPPER, "revocation-reason|" + reason)` (keyed so low-entropy reasons can't be brute-forced). Revoked certs ALWAYS return revoked verdict even on hash match.

**D3 — Issuance handshake (brief §9, mandatory).**
- `POST /api/certificates/issue/prepare`: JWT + institution approved + issuer wallet association checked server-side; PDF magic-byte/size/page validation; SHA-256 of original bytes; duplicate document_hash + duplicate (institution, certificate_number) guards (against certificates AND live intents); CERT-id + hashes; AES-256-GCM; Pinata pin; `issuance_intents` row `prepared` with payload JSONB + `expires_at` (30 min default); returns unsigned tx data (certificateIdHash, institutionIdHash, holderIdentityHash, documentHash, metadataHash, ipfsCID, supersedes, expiresAt, issuerWallet, contractAddress, chainId). NO certificate row yet.
- Frontend `services/wallet.js`: MetaMask detect → connect → chain 80002 verify/switch → connected account MUST equal intent issuerWallet → `BrowserProvider` + ethers Contract → `issueCertificate` → wait receipt → txHash. Error taxonomy handled: user rejection (4001), insufficient funds, wrong network, unauthorized issuer revert, contract revert reason, RPC failure, timeout. Private key never leaves MetaMask.
- `POST /api/certificates/issue/confirm` {certificateId, txHash}: backend INDEPENDENTLY verifies receipt (status 1, to == CONTRACT_ADDRESS, chainId 80002), parses `CertificateIssued` event, matches certIdHash/documentHash/metadataHash/institutionIdHash/issuer/ipfsCID/expiry against the intent, checks not revoked. Only then: intent → confirmed, authoritative certificate row inserted (unique certificate_id makes it idempotent), tx_hash + block_number stored, final QR generated, `issued` audit event. Repeated confirms return the same receipt. **Reconciliation**: if DB write fails after chain success, intent stays `submitted` with tx_hash persisted; confirm is retryable; `GET /api/certificates/issue/intents/:certificateId` exposes recovery status; never report failure without txHash + recovery path (brief §9).
- Orphaned ciphertext from rejected/abandoned signings: intent expires → status `expired`; ciphertext remains pinned (documented; optional unpin job later).

**D4 — Extraction (brief §6, text-only to Gemini).** `pdfParser.js` (pdf-parse v2 class API; text + page count + per-page blocks; configurable sufficiency threshold `PDF_TEXT_MIN_CHARS` default 200; page cap `MAX_PDF_PAGES` default 10) → if insufficient: render via pdfjs-dist (existing pdf-to-png-converter + sharp pipeline, 1600px JPEG) → `ocr.js` Tesseract locally (limits: pages, dimensions, `OCR_TIMEOUT_MS`, new `OCR_MAX_CONCURRENT` semaphore) → combine/clean text (page markers, whitespace normalization) → `gemini.js` structures TEXT ONLY (responseMimeType json + responseSchema; retry/backoff/budget/fatal-classification reused from ai.js; `GEMINI_MODEL` configurable; key backend-only). **Deleted paths: whole-PDF base64, Gemini vision images** — pixels never leave the server. Output: 17 base fields (brief §6) + per-field confidence + stated-vs-inferred flag + optional supporting fragment; never guess missing values (empty string). `certificateTemplates.js`: per-certificateType extra-field definitions → dynamic schema extension; extras persisted in `certificates.extra_data` JSONB and rendered in the review form. Human review/approval mandatory before prepare (brief §6 stage 5); AI output is never authenticity proof.

**D5 — Identity (`certificateIdentity.js`).** `generateCertificateId()` = `CERT-` + 8 hex from uuidv4 (random, never PII-derived); `certificateIdHash = keccak256(utf8(id))`; `holderIdentityHash = HMAC(HASH_PEPPER, "holder|" + norm(name) + "|" + norm(identifier))`; `institutionIdHash = HMAC(HASH_PEPPER, "institution|" + institution_id)` (stable per institution, human id `INST-XXXXXXXX`); `metadataHash = SHA-256(canonicalJson(approved metadata + institutionIdHash))` — covers institution identity per brief §7; `documentHash = SHA-256(original PDF bytes)`; AES-256-GCM with `DOCUMENT_ENC_KEY` (iv/tag hex in DB). Same keyed/plain/keccak three-family design as NOSIH. New 64-hex keys recommended (cert identity space is independent of land).

**D6 — Database (additive, non-destructive; brief §8/§19).** One documented migration `backend/supabase/migrations/001_certichain.sql` + refreshed `schema.sql` for fresh installs. BEFORE applying: backup (Supabase dashboard backup or `pg_dump` via DATABASE_URL — user-run/approved). New tables: `institutions` (INST id, verification_status pending/approved/rejected/suspended, approved_by/at, wallet config), `issuer_wallets` (wallet unique → one institution, authorization_tx_hash), `certificates` (all brief §8 fields incl. extra_data JSONB, supersedes_certificate_id, status active/revoked/expired/superseded), `issuance_intents` (prepared/submitted/confirmed/failed/expired, payload JSONB, expires_at), `certificate_events` (issued/verified/revoked/reissued/expired/superseded, performed_by nullable for public verifies). `users`: ADD `institution_id` FK nullable; role check extended to platform_admin/institution_admin/issuer/auditor (legacy admin/issuer values kept; seed maps existing admin → platform_admin). Land tables (`land_records`, `owners`) and their data UNTOUCHED — no reset script run. RLS enabled + zero public policies on every new table; service-role key backend-only. FKs, unique constraints (certificate_id, certificate_id_hash, document_hash, (institution_id, certificate_number) where present, wallet_address), indexes (cert id/hash, institution, wallet, status, created_at desc). Institution scoping enforced in middleware on EVERY query — never trust client-supplied institution id (brief §18). Expiry: `expired` is computed from expiry_date at read/verify time and lazily mirrored to status + `expired` event.

**D7 — Verification (chain-authoritative; brief §10).** `GET /api/verify/:certificateId` public, rate-limited (`express-rate-limit`, ~60/min/IP). Sequence: validate CERT id → chain `certificateExists`/`getCertificate` FIRST → Supabase row → compare documentHash, metadataHash, issuer wallet, institutionIdHash, ipfsCID → revocation (chain flag authoritative) → expiry (chain expiresAt). Verdicts: authentic-active / revoked / expired / superseded (points to new CERT id) / document-mismatch / metadata-mismatch / issuer-unauthorized / not-found / db-chain-mismatch / **blockchain-unavailable → indeterminate (503), NEVER valid-from-DB**. Public payload per brief example (holderName, type, course, qualification, issueDate, institution name+verified, issuerWallet, txHash, chainId, status flags) — no gov-ID refs, no encryption details, no extra_data. `verified` audit event written async. Tamper (brief §11): `POST /api/verify/:certificateId/tamper-check` — Mode A (no file): chain hash → IPFS ciphertext → backend decrypt → rehash → intact verdict (contents not exposed); Mode B (uploaded PDF): magic bytes → SHA-256 exact bytes → compare vs CHAIN hash → exact/modified/unregistered/revoked/mismatch verdicts. No AI in integrity checks.

**D8 — Reissuance (brief §12).** `POST /api/certificates/:id/reissue` → new prepare flow prefilled from old metadata, `supersedesCertificateIdHash` = old id hash (contract requires target exists). Old chain record NEVER modified; on confirm of the new cert, old DB status → `superseded` + `reissued`/`superseded` events; both visible in history; verifying old id returns superseded verdict + new CERT id.

**D9 — Frontend (brief §14; CRA preserved).** Strip ALL tour code (fixes broken build). Keep design system: graphite/soft-white tokens (#F2F3F5/#1E2126/#3E444C, success #3D8B6E, danger #B84040, warning #C4943A), Inter/Courier New, Lucide strokeWidth 1.75, semantic CSS classes, ErrorBoundary + apiErrorMessage + shape guards. New structure per brief: components (ProtectedRoute role-aware, WalletConnect, CertificateUpload, CertificatePreview, VerificationResult, QRDisplay, TransactionStatus), pages (Login, Dashboard, Issue, Certificates, CertificateDetails, Verify, Tamper, Institutions), services (wallet.js, contract.js), utils (api.js adapted, contractABI.js generated from artifacts by script, certificateHelpers.js). IssuePage states: upload → extracting (text/OCR/Gemini progress) → review (editable form + confidence + source-PDF preview) → wallet (connect/network/account match) → signing (MetaMask progress) → confirming → receipt (QR + txHash + explorer link). QR encodes `/verify?certificateId=…` — phone camera opens it directly (no in-app camera dep; matches NOSIH pattern). Dashboard: institution-scoped counts (total/active/revoked/expired) + recent issuance/verification activity; platform_admin sees institutions count + platform-wide. Revoke UI: proper modal with required reason (replaces window.prompt). Session auth stays sessionStorage + /auth/me validation.

**D10 — Env / deployment.** `.env.example` rewritten per brief §16: drops ISSUER_PRIVATE_KEY/ADMIN_* land leftovers; adds REVOKE_PRIVATE_KEY, REACT_APP_CONTRACT_ADDRESS, REACT_APP_CHAIN_ID; keeps root-.env single-source convention (`env.js` first import). Required-at-boot: SUPABASE_URL, SUPABASE_SERVICE_ROLE_KEY, JWT_SECRET, DOCUMENT_ENC_KEY, HASH_PEPPER, CONTRACT_ADDRESS (chain reads); feature-gated: GEMINI_API_KEY (extraction), PINATA_JWT (issuance), REVOKE_PRIVATE_KEY (revocation). `scripts/deploy.js` deploys CertificateRegistry, prints address/chainId/admin, saves ABI + `deployments/amoy.json`; `addIssuer.js` requires an approved institution record and derives institutionIdHash (no arbitrary wallets); `removeIssuer.js` added. Vercel: wrapper/rewrites unchanged; `vercel-env.mjs` push list updated (REACT_APP_* are BUILD-time — must exist before `vercel-deploy`); preflight updated for new services/ABI. **All live-chain writes (deploy, authorizeIssuer, acceptance issuances/revocations) happen only at P9 with explicit user go-ahead and funded wallets** — standing rule: no test writes to the ledger; all contract tests run on in-memory Hardhat network.
